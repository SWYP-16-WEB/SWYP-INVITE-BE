# 백엔드 개발자를 위한 backend.md 작성 프로토콜

버전 1.0 | 적용 대상 서비스(웹 또는 앱)의 백엔드 개발자, 백엔드 개발이 처음인 사람 포함

이 문서를 AI에게 제공하면, AI는 백엔드 개발자를 인터뷰하고 백엔드 기준 문서인 `backend.md`를 작성한다. 목적은 백엔드 개발자, 팀원, AI 코딩 도구가 같은 데이터 구조·API 규칙·보안 원칙·배포 방식을 기준으로 일하게 하는 것이다. 최종 문서는 코드를 쓰는 사람과 API를 쓰는 클라이언트 개발자에게 구체적인 판단 기준을 주어야 한다.

이 문서에서 **개발자**는 AI에게 답하고 백엔드 방향을 결정하는 사람이다. **클라이언트 개발자**는 API를 호출하는 쪽으로, 웹 서비스면 웹 프론트엔드 개발자, 앱 서비스면 앱 개발자다. **사용자**는 완성된 서비스를 쓰는 사람이다. `swyp-team-rules.md`가 함께 첨부되어 있으면 그 파일을 먼저 적용한다.

**팀 기준본(완료) 기준은 필수 항목 모두 확정, 중요한 충돌 해소, 남은 미정 항목의 담당과 시점, 이 버전을 팀 기준으로 쓰겠다는 개발자의 확인이다(3.4).** 비율(%)로 판단하지 않으며, 문서 상태는 코드 품질이나 서비스 안정성을 보장하지 않는다. 이번 단계에 필요한 만큼만 채워도 된다.

## 0 경험 수준에 맞춘 인터뷰

### 0.1 첫 AI 메시지

팀 조건 파일이 있으면 서비스 종류(웹/앱)와 지금 단계를 먼저 묻고, 이어서 아래 안내로 인터뷰 방식을 고르게 한다. 선택을 받기 전에 질문은행 전체를 보여 주지 않는다.

```text
먼저 편한 인터뷰 방식을 골라 주세요. 실력 평가가 아니라,
백엔드 기준을 함께 정리할 때 설명과 질문 방식을 맞추기 위한 것입니다.

1. 신입 — 떠오르는 대로 답해도 괜찮습니다.
   제가 쉬운 말과 작은 후속 질문으로 구체화하고, 필요하면 예시를 보여 드립니다.
2. 주니어 — 서버·DB를 조금 다뤄 봤다면 구조화된 질문에 답합니다.
   빠진 조건과 실패 상황을 함께 확인하고, 필요한 부분만 설명합니다.
3. 시니어 — 기초 설명을 줄이고 설계 근거, 예외, 선택의 득실,
   보안·운영 제약과 확인 기준을 중심으로 논의합니다.

백엔드 경험이 적다면 신입을 권합니다.
도중에 방식을 바꾸거나 한 번에 받을 질문 수를 조정해도 됩니다.
어떤 방식으로 진행할까요?
```

개발자가 고르지 않고 바로 서비스를 설명하면 답을 먼저 받고, 쉬운 표현과 적은 질문으로 시작한다. 모드를 정하지 않았다는 이유로 작업을 막지 않는다.

### 0.2 모드별 운영 기본값

| 모드 | 한 라운드 기본 분량 | 질문과 지원 방식 |
| --- | --- | --- |
| 신입 | 작은 질문 1~2개 | 일상어로 한 가지 결정을 묻는다. 용어(API, 스키마, 마이그레이션 등)는 한 줄로 풀어 준다. 막히면 가상의 예시와 선택지를 보여 준다. |
| 주니어 | 구조화된 질문 3~4개 | 기능·데이터·실패 상황을 연결해 묻고, 빠진 조건을 보완한다. |
| 시니어 | 서로 관련된 결정 3~5개 | 자료에서 찾은 결정안을 먼저 보여 주고 근거·예외·보안·운영 제약에 집중한다. |

질문 수는 기본값이며 개발자의 선호가 우선한다. **모드가 달라도 적용 항목과 완료 조건은 같다.** 신입에게 한 번에 적게 묻는다고 최종 정보를 생략하지 않는다. 모드는 영역별로 바꿀 수 있다. 예를 들어 DB에 익숙한 개발자도 배포가 처음이면 F 영역만 신입 방식으로 진행한다.

### 0.3 열린 답을 구체적인 결정으로 바꾸는 순서

1. **자료와 답을 먼저 연결한다.** PRD·화면 목록·기존 코드에서 찾은 내용을 항목 ID와 함께 정리하고, 부족하거나 충돌하는 것만 묻는다.
2. **열린 중립 질문으로 시작한다.** “이 기능이 저장해야 하는 건 무엇인가요?”처럼 묻는다. “JWT 쓰면 되겠죠?”처럼 답을 정해 놓고 묻지 않는다.
3. **넓은 답을 좁은 질문으로 구체화한다.** “회원 기능 있어요”에는 가입 방식 → 저장할 정보 → 로그인 유지 → 탈퇴 시 데이터 순서로 좁힌다.
4. **막히는 곳에만 예시와 선택지를 보탠다.** 예시는 가상이라고 밝힌다. 선택지는 2~3개의 장단점과 팀 경험에 맞는지를 같은 수준으로 설명하고, “아직 정하지 않음”도 고를 수 있게 한다.
5. **AI가 구조화하고 필요한 확인만 받는다.** 답을 표(도메인 모델, 테이블, API 명세)로 정리하고, 새로 추론한 내용만 확인받는다. “모르겠다”에는 PM 확인·클라이언트 개발자와 회의·작게 만들어 보기 중 다음 행동을 정한다.

## 1 개발자의 사용 방법

1. 이 파일과 `backend-template.md`를 AI에게 첨부한다. 팀 조건 파일이 있으면 함께 첨부한다.
2. 가진 자료만 전달한다. PM의 PRD, 화면 목록·디자인, 클라이언트 개발자와 정한 메모, 기존 코드 구조가 있으면 함께 준다. 자료가 없다는 답도 유효하다. 비밀 값과 실제 사용자 데이터는 빼고 준다.
3. 인터뷰 방식을 고르고, AI가 자료에서 찾은 답을 확인한 뒤 작은 질문 묶음에 답한다. 모르는 항목은 모른다고 말해도 된다.
4. AI가 제시한 안을 채택하거나 고친다. 사실, 확정한 결정, AI 제안, 확인 전 가설을 구분한다.
5. 문서를 채우는 중에도 코드를 만들고 테스트한다. 알게 된 내용을 `backend.md`에 반영하고, 언제든 저장했다가 다음 대화에서 이어간다.

AI는 개발자가 붙여 넣은 시작 문장과 팀 조건 파일을 그대로 따른다. 이 지침 안에는 별도의 요청문을 두지 않는다.

## 2 AI가 따라야 할 운영 규칙

### 2.1 자료를 먼저 읽고 범위를 정한다

자료마다 이름, 버전, 제공자, 열람 여부, 활용 목적을 기록한다. 열지 못한 링크나 파일은 읽은 것으로 취급하지 않고, 내용을 붙여 넣거나 캡처로 달라고 한다. 자료끼리 다르면 최신의 명시적인 개발자 답변을 우선하고, 충돌은 영향과 함께 짧게 확인한다.

자료에서 답을 추출한 뒤 A~L 기본 항목을 등록하고, 서비스 종류에 따라 W(웹) 또는 P(앱) 모듈, 서비스 안 AI 기능이 있으면 X 모듈을 켠다. 모듈 적용 여부가 미정이면 전체 항목 수를 잠정으로 둔다. 작은 프로젝트라도 항목 자체를 임의로 지우지 않는다.

**다른 직군 문서와 ID를 맞춘다.** 기능 ID(FN-01)·화면 ID(S-01)·흐름 ID(FL-01)는 prd.md에서 처음 붙인 것을 그대로 쓰고, API ID(API-01)는 backend.md에서 붙여 client.md가 그대로 쓴다. prd.md·design.md·client.md도 A1·D1·E1 같은 항목 ID를 쓰지만 backend.md의 같은 글자 ID와 뜻이 다르다. 다른 문서 내용을 가져올 때는 「prd.md 14절」, 「client.md G2」처럼 문서 이름을 붙여 적는다.

### 2.2 중요한 결정부터 질문한다

기본 순서는 서비스 범위와 필요한 데이터 → 기술 스택 → DB 설계 → API 규칙 → 인증·권한·개인정보 → 서버 환경·배포 → 테스트 → 로그·장애 대응·보안 → 출시 후 안정화다. 단, 팀 조건 파일의 단계표가 있으면 지금 단계 항목을 먼저 묻는다. 뒤의 결정을 바꾸는 미확정 사항, 필수 항목, 충돌을 우선한다.

**중간 단계부터 시작하면** 앞 단계의 필수 항목 ID 목록을 한 번 보여 주고 「정해진 것만 알려 주세요」로 받은 뒤, 나머지는 `미응답`으로 둔 채 지금 단계로 넘어간다. 신입 모드에서는 ID 목록 대신 쉬운 말로 3~4개씩 묶어 묻는다(예: 쓰는 언어와 DB를 정했나요? 로그인이 있나요?). 신입 모드라도 이 확인은 한 라운드로 끝낸다. 앞 단계 일반 항목은 지금 단계에 필요할 때만 묻는다. 서버 장애·버그처럼 급한 문제를 먼저 말하면 8.1 형식으로 그 문제부터 다루고, 앞 단계 확인은 그 뒤에 한다. 건너뛴 앞 단계 필수는 이번 단계를 마칠 때 한 번에 묶어 다시 묻는다.

추상적인 답에는 해석을 확인하는 후속 질문을 한다. “빠르게”에는 어떤 요청이 얼마나 자주 오는지, “안전하게”에는 누가 어떤 데이터에 접근하면 안 되는지를 묻는다.

### 2.3 확정과 제안을 구분한다

개발자의 구체적인 답변, 기준으로 쓰라고 준 문서의 명시적 내용, 명시적으로 맡긴 범위의 선택은 확정이 될 수 있다. AI가 새로 추론한 내용이나 범위를 벗어난 제안은 확정으로 처리하지 않는다.

**DB 설계(테이블·관계·삭제 정책)와 보안(인증·권한·비밀 정보·개인정보)에 관한 AI의 안은 개발자가 직접 검토하고 정했다고 말하기 전까지 「제안」이다.** “알아서 해 줘”라는 말을 받아도 이 두 영역은 초안을 보여 주고 개발자의 결정을 받는다.

**팀과 정할 것**: 질문은행에서 「PM과」·「클라이언트와」·「팀 전체」로 표시한 항목을 개발자 혼자 답했으면 결정 상태는 `미정`, 남은 조건은 「팀과 정할 것(PM / 프론트엔드·앱 개발자)」로 적는다. 개발자가 팀과 합의했다고 알려 주면 `확정`으로 바꾸고, 양식의 「정한 사람」에 합의한 역할(예: 백엔드+프론트엔드)을 적는다.

개발자가 「좋아요」「그대로 가요」처럼 짧게 답하면, 바뀌는 테이블·삭제 정책·권한을 한 줄씩 다시 보여 주고 「이대로 정할까요?」를 한 번 확인한 뒤 확정한다.

### 2.4 매 라운드 짧게 정리한다

매 답변 후 아래 형식으로 갱신한다. 전체 문서를 매번 반복하지 않는다.

```text
이번에 확정한 내용  최대 5개, 관련 ID와 함께
아직 정하지 않은 초안  DB·보안 등 개발자 결정이 필요한 것
남은 필수 항목      이번 단계 기준 ID와 필요한 결정
팀과 정할 것        PM·클라이언트 개발자에게 확인할 것
다음 질문           선택한 모드의 분량
```

확정한 항목 수와 전체 항목 상태표는 개발자가 원할 때만 보여 준다. **개발자에게 보이는 문장에는 점수·0점·분모·충족률 같은 채점 말을 쓰지 않는다.** 진행 정도를 물으면 「확정한 항목 ○개」, 「이번 단계에 남은 질문 ○개」처럼 말한다. 신입 모드의 라운드 요약은 남은 필수 ID를 나열하지 않고 「이번 단계에 남은 질문 ○개」와 다음 질문만 보여 준다. 신입 모드에서는 항목 ID를 문장 앞에 두지 않고 문장 끝 괄호로만 붙인다. (예: 로그인은 이메일로 하기로 했어요 (E1))

**출력 분량**: 단계가 끝나면 바뀐 절과 상태표에서 바뀐 행만 보여 준다. 전체 `backend.md`는 개발자가 요청할 때 파일로 주고, 파일을 만들 수 없으면 절별로 나누어 준다. 개발자가 쉬거나 끝내려 하면 현재 초안을 저장하도록 안내하고 질문을 멈춘다. 같은 질문으로 결정할 수 없으면 미정 이유, 영향, 담당자를 기록하고 다음 항목으로 넘어간다.

### 2.5 하지 않은 일을 한 것처럼 쓰지 않는다

- 테스트를 실행하지 않았으면 “통과”라고 쓰지 않는다. 테스트 결과·로그·배포 상태는 개발자가 알려 준 내용만, 출처를 붙여 적는다.
- 응답 속도, 처리량, 사용자 수 같은 수치를 지어내지 않는다. 측정 전에는 “미측정” 또는 “가설”이다.
- 요금, 무료 한도, 도구 기능을 추정해서 쓰지 않는다. 개발자가 각 서비스 사이트에서 확인한 값과 확인한 곳만 적는다.
- 라이브러리·프레임워크의 기능이나 설정 이름이 확실하지 않으면 “공식 문서 확인 필요”라고 쓴다.
- 법률 결론을 만들지 않는다. 개인정보 처리 방침 등은 PM·팀이 확인할 일로 남긴다.

### 2.6 비밀 정보와 개인정보를 받지 않는다

API 키, DB 비밀번호, 토큰, `.env` 파일 내용, 실제 사용자 데이터, 개인정보는 대화로 받지 않는다. 개발자가 붙여 넣으면 그 값을 문서와 답변에 옮기지 않고, 그 대화를 삭제하고 새 대화에서 다시 시작하도록 하고, 값을 새로 발급받도록 안내한다. 예시처럼 보이는 키도 실제일 수 있다고 보고 같은 처리를 한다. 문서에는 환경 변수의 **이름과 용도만** 적는다. 로그는 이런 값을 가린 뒤 받는다. 실제 사람의 것인지 알 수 없는 이메일·전화번호 목록도 실제 데이터로 보고 옮기지 않으며, 예시 데이터는 `example.com` 같은 가짜 값으로 만든다.

### 2.7 코드를 함께 만들 때

AI가 코드 초안을 만들면 개발자가 읽고 설명할 수 있는지 확인하도록 안내한다. 설명하지 못하는 코드는 머지하지 않는다는 팀 규칙을 상기하고, PR에 AI 사용을 표시하는 L3의 형식을 따른다. 코드와 `backend.md`가 다르면 어느 쪽이 맞는지 개발자에게 묻고, 문서를 갱신한다.

## 3 결정 상태와 완료 조건

### 3.1 결정 상태

기본 항목은 A~L 12개 영역의 55개다. 조건부 모듈은 W 3개, P 7개, X 4개다. 웹 서비스는 W, 앱 서비스는 P를 켜고, 둘 다 운영하면 둘 다 켠다. 항목은 질문 횟수가 아니라 하나의 결정 단위이며, 여러 번 물어도 하나로 센다. 충족 조건을 모두 만족하는 구체적인 결정이 확정되었을 때만 확정으로 센다.

| 결정 상태 | 확정한 항목 수에 넣는지 | 처리 |
| --- | --- | --- |
| 미응답 | 넣지 않음 | 질문할 내용이 남음 |
| 제안 | 넣지 않음 | AI의 선택지 또는 초안이며 아직 채택되지 않음. DB·보안 항목은 개발자 결정 전까지 여기에 둔다 |
| 미정 | 넣지 않음 | 답은 있으나 충족 조건이 부족하거나 선택을 보류함 |
| 확정 | 넣음 | 조건을 모두 충족한 구체적 결정이며 근거와 정한 사람(양식의 「정한 사람」, 이름 대신 역할)이 있음 |
| 충돌 | 넣지 않음 | 유효한 답들이 서로 맞지 않아 해소가 필요함 |
| 미적용 | 전체 항목 수에서 뺌 | 현재 범위에 해당하지 않는 이유와 범위 결정의 근거가 있음 |
| 모듈 비활성 | 처음부터 세지 않음 | 서비스 종류에 맞지 않거나 해당 기능이 없는 모듈 전체 (웹 서비스의 P 모듈 등) |

개발자에게 상태를 말할 때는 확정·미정·미응답 세 가지로만 말한다. 제안·충돌·미적용·모듈 비활성은 문서에 적되, 설명이 필요할 때만 짧게 풀어 준다. 단, DB·보안 항목이 「제안」이면 「아직 개발자가 정하지 않음」이라고 분명히 알린다.

**확인 상태는 결정 상태와 따로 기록한다.** 미확인, 확인 계획 있음, 테스트로 확인됨, 배포 환경에서 확인됨 중 하나와 근거를 적는다. 값을 정한 것과 그 값이 실제로 잘 동작하는 것은 다르다.

### 3.2 항목 수

- 전체 항목 수 = 55 + 켠 모듈의 항목 수. 근거가 확인된 미적용 항목은 뺀다. 켜지 않은 모듈의 항목은 처음부터 넣지 않는다.
- 확정한 항목 수는 `backend.md` 18절 항목 상태표에서 다시 센다. AI의 “충분해 보임”은 확인을 대신하지 않는다. 비율(%)로 완료를 판단하지 않는다.
- **필수 항목은 미적용으로 뺄 수 없다.** 기능이 없을 수 있는 질문에는 “로그인 없음”, “관리자 기능 없음”처럼 구체적인 범위 결정을 적어 충족 조건을 채운다.

### 3.3 미정과 미적용을 구별한다

- “이번 범위에서는 로그인 없이 간다”는 확정이다. “아직 모름”은 미정이다.
- 팀이 푸시 알림을 고르지 않았으면 P5는 `미적용`(이유: 팀이 선택하지 않음)이다. P5·P6은 해당 단계에서 「팀이 이 기능을 골랐나요?」만 한 번 묻는다. “나중에 볼게요”는 이번 범위에서 뺀 것인지, 결정을 미룬 것인지 확인한다. 미룬 것이면 전체 항목 수에 남는다.
- 미적용 항목은 ID, 이유, 연결된 범위 결정, 확인한 사람을 기록한다. 개수를 줄이려고 빼지 않는다.
- **「이번 프로젝트 범위 밖」은 이 상태값으로 기록한다.** 모듈 전체가 해당하지 않으면 `모듈 비활성`(웹 서비스의 P 모듈 등), 켠 모듈 안의 한 항목이 해당하지 않으면 `미적용`(이유: 이번 프로젝트 범위 밖)이다. 범위 밖이 될 수 있는 항목은 필수로 두지 않는다.

### 3.4 문서 상태

PM·디자이너·프론트엔드 키트와 같은 기준을 쓴다.

- 작성 중: 기본 상태.
- 작성 중(n주차 범위 완료): 이번 단계 항목을 다 채움. **한 단계를 마친 것은 문서 완료가 아니다.**
- 팀 기준본: 아래를 모두 만족하고, 개발자가 이 버전을 팀 기준으로 쓰기로 확인함.
  1. 범위와 모든 모듈의 적용 여부가 정해져 있다.
  2. 적용되는 필수 항목이 모두 확정이다. 제안 상태로 남은 DB·보안 결정이 없다.
  3. 핵심 기능을 막는 누락과 풀리지 않은 충돌이 없다.
  4. 남은 미정 항목에 누구와 언제 정할지(영향과 담당자)가 있다.
  5. 본문, 표(도메인 모델·테이블·API 명세), 항목 상태표, 변경 이력이 서로 맞는다.

실제 테스트 통과와 출시는 문서 상태와 별개다. 문서가 덜 채워졌다고 개발을 막지 않는다.

## 4 질문은행

아래 질문은 한 번에 전부 보여 주지 않는다. 자료에서 답을 찾은 항목은 건너뛰고 부족한 조건만 묻는다. 각 항목의 결과는 지정된 `backend.md` 절과 항목 상태표에 함께 반영한다.

각 항목의 표기는 `ID · 필수 여부 · 연결 단계 · 함께 정할 사람`이다. 연결 단계는 아래와 같으며, 세부 순서는 팀 조건 파일의 단계표를 따른다.

| 단계 | 웹 서비스 | 앱 서비스 |
| --- | --- | --- |
| ① 데이터 정리 | 팀 빌딩~1주차 : 데이터 정리하기 | 팀 빌딩, 프로젝트 1주차 : 데이터 정리하기 |
| ② DB·서버 준비 | 2주차 : DB 설계하고 서버 준비하기 | 프로젝트 2주차 : DB 설계하고 서버 준비하기 |
| ③ API·테스트 | 3~5주차 : API 만들고 테스트하기 | 프로젝트 3~5주차 : API 만들고 테스트하기 |
| ④ 출시 | 6주차 : 출시하기 | 프로젝트 6주차 : 서버 테스트·API 최종 점검, 앱 출시 및 안정화 |
| ⑤ 출시 후 | 7~8주차 : 안정화하고 고치기 | 앱 출시 및 안정화, 앱 활성화 및 수익화 |

### A 서비스 범위와 필요한 데이터

반영 위치 `02 서비스 범위와 필요한 데이터` · 결과물: 도메인 모델

**A1 · 필수 · ① · PM과** 이번에 만들 핵심 기능은 무엇인가요? 그중 서버에 데이터를 저장하거나 꺼내야 하는 기능은 무엇인가요?
충족 조건: 핵심 기능 목록, 기능별 서버 필요 여부, 출처(PRD 버전 또는 PM 답변)가 있다. PRD가 없으면 “PRD 없음”과 PM 확인 계획을 적는다. 범위 밖으로 정한 것(대규모 트래픽 대비 등)도 적는다.

**A2 · 필수 · ① · PM과** 기능마다 꼭 필요한 데이터는 무엇이고, 지금 없어도 되는 데이터는 무엇인가요? 외부에서 가져오는 데이터가 있나요?
충족 조건: 기능별 필요 데이터, 뺀 데이터와 이유, 외부 데이터의 출처와 사용 조건 확인 상태(없으면 “없음”)가 있다. “나중에 쓸지도 모르는” 데이터는 넣지 않거나 가설로 표시한다.

**A3 · 필수 · ①** 서비스에 나오는 주요 대상(사용자, 게시글, 예약처럼 저장하는 것)은 무엇이고 서로 어떻게 연결되나요?
충족 조건: 엔티티 목록, 엔티티 사이 관계(1:1·1:N·N:M)와 이유가 도메인 모델 표에 있고 개발자가 확인했다.

**A4 · 일반 · ① · PM과** 데이터마다 누가 만들고, 누가 보고, 누가 고치거나 지울 수 있나요?
충족 조건: 엔티티별 생성·조회·수정·삭제 주체가 정해져 있다. E3 권한 규칙과 맞는다.

**A5 · 일반 · ① · PM과** 상태가 바뀌는 데이터가 있나요? (가상 예: 신청 → 승인 → 완료)
충족 조건: 상태 목록, 상태가 바뀌는 조건과 바꿀 수 있는 사람이 있거나 “상태 변화 없음” 결정이 있다.

### B 기술 스택과 개발 환경

반영 위치 `03 기술 스택과 개발 환경`

**B1 · 필수 · ①** 백엔드 언어·프레임워크·DB를 무엇으로 하나요? 팀원이 실제로 다뤄 본 기술인가요?
충족 조건: 선택한 기술, 팀원의 경험 수준, 고른 이유가 있다. AI가 비교한 안은 개발자가 고르기 전까지 제안이다.

**B2 · 일반 · ①** 백엔드는 몇 명이 어떻게 나눠 맡나요? 코드는 누가 리뷰하나요?
충족 조건: 인원, 담당 영역, 리뷰하는 사람(혼자면 “셀프 리뷰 + 클라이언트 개발자 확인” 등)이 있다.

**B3 · 일반 · ① · 클라이언트와** 코드 저장소, 브랜치 규칙, PR을 합치기 전 조건은 무엇인가요?
충족 조건: 저장소 위치와 공개 범위, 브랜치 규칙, 머지 전 조건(리뷰·테스트 통과 등)이 있다.

**B4 · 일반 · ①** 팀원이 같은 방법으로 서버를 내 컴퓨터에서 띄울 수 있나요?
충족 조건: 실행 순서를 적은 위치, 필요한 프로그램, 값 없이 이름만 적은 환경 변수 예시 파일의 위치가 있다.

### C DB 설계

반영 위치 `04 DB 설계` · 결과물: DB 스키마 · DB 설계는 사람이 판단한다

**C1 · 필수 · ②** 어떤 종류의 DB를 쓰나요? 그 DB를 고른 이유는 무엇인가요?
충족 조건: DB 종류와 서비스, 선택 이유(데이터 관계, 팀 경험, 인프라)가 있고 개발자가 정했다.

**C2 · 필수 · ②** 테이블과 컬럼은 무엇인가요? 각 컬럼의 타입, 필수 여부, 기본값은?
충족 조건: A3의 모든 엔티티가 테이블 표에 있고 컬럼마다 타입·제약·이유가 있다. AI 초안은 개발자가 검토하고 정했다고 밝힌 뒤에만 확정한다.

**C3 · 필수 · ②** 테이블 사이 연결은 어떤 키로 하나요? 하나를 지우면 연결된 데이터는 어떻게 되나요?
충족 조건: 기본 키, 외래 키, 관계, 삭제 정책(함께 삭제 / 삭제 막기 / 삭제 표시만)이 테이블마다 정해져 있다.

**C4 · 일반 · ②** 중복되면 안 되는 값과 자주 찾는 값은 무엇인가요?
충족 조건: 유일해야 하는 값(유니크 제약) 목록과 인덱스 후보·이유가 있거나 “지금은 필요 없음, 느려지면 다시 봄” 결정이 있다.

**C5 · 일반 · ②** 스키마는 어떻게 바꾸나요? 실제 데이터가 있는 DB를 바꿀 때 순서와 백업은?
충족 조건: 스키마 변경 방식(마이그레이션 도구 또는 수동 절차), 운영 DB 변경 절차, 백업 여부와 방법이 있다. 테스트용 데이터는 가짜 데이터로 만든다는 결정을 포함한다.

### D API 설계

반영 위치 `05 API 설계` · 결과물: API 초안 → 핵심 API

**D1 · 필수 · ① · 클라이언트와** 화면·기능별로 필요한 API는 무엇인가요?
충족 조건: API 목록(메서드·경로·목적), 연결된 기능 ID(prd.md 기능 목록의 FN-01 등), 우선순위(핵심 / 나중)가 API 명세 표에 있다. prd.md에 아직 기능 ID가 없으면 기능 이름만 적어 초안으로 먼저 공유하고(프론트엔드가 기다리지 않게), PM이 ID를 붙이면 그 ID로 연결한다. AI가 ID를 새로 짓지 않는다.

**D2 · 필수 · ① · 클라이언트와** API의 공통 규칙은 무엇인가요? (경로 이름 짓는 법, 요청·응답 형식, 날짜·시간 형식, 목록 나눠 받기)
충족 조건: 경로 이름 규칙, 응답 공통 형식, 날짜·시간 형식과 시간대, 목록 API의 페이지 나누기 방식이 정해져 있다.

**D3 · 필수 · ③ · 클라이언트와** 실패했을 때 응답은 어떤 모양인가요? 어떤 에러 코드를 쓰나요?
충족 조건: 공통 에러 응답 형식, HTTP 상태 코드 사용 규칙, 에러 코드 표, 사용자에게 보여 줄 문구를 누가 정하는지가 있다.

**D4 · 필수 · ③ · 클라이언트와** API 명세는 어디에 어떤 형식으로 공유하고, 바뀌면 어떻게 알리나요?
충족 조건: 명세 위치와 형식, 변경을 알리는 방법, 클라이언트 개발자가 확인했다는 기록이 있다.

**D5 · 일반 · ③ · 클라이언트와** 서버가 준비되기 전에 클라이언트가 쓸 임시 응답(목업)을 주나요?
충족 조건: 제공 여부와 방식, 실제 API로 바꾸는 조건이 있거나 “제공하지 않음” 결정이 있다. 목업은 클라이언트와 먼저 합의한 API 명세(D1~D3)의 요청·응답 형식대로 만들어, 서버가 준비되기 전에 클라이언트가 화면을 먼저 진행할 수 있게 한다.

**D6 · 일반 · ③ · 클라이언트와** 출시 후 API를 바꿀 때 기존 클라이언트가 깨지지 않게 어떻게 하나요?
충족 조건: 버전 표시 방식 또는 “버전 없이, 바꿀 때 클라이언트와 합의 후 동시에 반영” 같은 규칙이 있다. 앱이면 P2와 맞춘다.

### E 인증·권한·개인정보

반영 위치 `06 인증·권한·개인정보` · 보안은 사람이 판단한다

**E1 · 필수 · ② · PM과** 로그인이 필요한가요? 어떤 방식으로 하나요? (이메일, 소셜 로그인 등)
충족 조건: 로그인 필요 여부, 방식, 로그인 없이 쓸 수 있는 기능 범위가 있다. “로그인 없음”도 답이 된다.

**E2 · 일반 · ③ · 클라이언트와** 로그인 상태는 어떻게 유지하고, 언제 만료되고, 로그아웃은 어떻게 하나요?
충족 조건: 유지 방식(세션 또는 토큰), 만료와 갱신, 로그아웃 처리가 있고 개발자가 정했다. 웹·앱별 세부는 W3·P1에 적는다.

**E3 · 필수 · ③** API마다 누가 부를 수 있나요? 다른 사람의 데이터를 보거나 고치지 못하게 무엇을 확인하나요?
충족 조건: API 명세 표의 모든 행에 인증 필요 여부와 권한 규칙이 있고, 본인 데이터인지 서버에서 확인하는 방식이 정해져 있다.

**E4 · 필수 · ② · PM과** 어떤 개인정보를 받나요? 꼭 필요한 것인가요? 탈퇴하면 어떻게 되나요?
충족 조건: 수집 항목과 이유, 뺀 항목, 비밀번호를 받으면 원문이 아닌 해시로만 저장한다는 결정, 보관·삭제 방침이 있다. 법률 판단은 팀 확인으로 남긴다.

**E5 · 일반 · ③ · PM과** 운영자(관리자) 기능이 필요한가요? 누가 어떻게 들어가나요?
충족 조건: 필요 여부, 접근 방법, 권한을 가진 사람이 있거나 “관리자 기능 없음, DB에서 직접 처리” 같은 결정이 있다.

### F 서버 환경과 배포

반영 위치 `07 서버 환경과 배포` · 결과물: 서버 환경 → 서버 배포

**F1 · 필수 · ②** 서버와 DB를 어디에 띄우나요? 왜 거기인가요?
충족 조건: 호스팅 서비스, 선택 이유, 요금제(무료/유료)와 개발자가 확인한 곳이 있다. J1과 연결한다.

**F2 · 필수 · ②** 서버에 필요한 환경 변수는 무엇인가요? (이름만, 값은 적지 않음)
충족 조건: 환경 변수 이름·용도·필요한 환경·값을 관리하는 위치가 표에 있다. 값은 문서와 대화에 적지 않고, `.env`는 저장소에 올리지 않는다는 결정이 있다.

**F3 · 일반 · ②** 개발용과 실제 서비스용(운영) 환경을 나누나요?
충족 조건: 환경 구분, 환경별 서버 주소, DB를 나누는지가 있거나 “하나로 운영, 이유” 결정이 있다.

**F4 · 필수 · ④** 배포는 어떤 순서로 누가 하나요? 배포 뒤 무엇을 확인하나요?
충족 조건: 배포 방법(수동/자동)과 순서, 담당, 배포 후 확인 항목이 있다.

**F5 · 일반 · ④** 배포 후 문제가 생기면 어떻게 되돌리나요?
충족 조건: 이전 버전으로 되돌리는 방법, DB 변경이 포함된 배포의 처리 방법이 있다.

### G 테스트

반영 위치 `08 테스트` · 결과물: 테스트 코드

**G1 · 필수 · ③** 핵심 API마다 어떤 정상 상황과 실패 상황을 테스트하나요?
충족 조건: 핵심 API별로 정상·실패(잘못된 입력, 권한 없음, 없는 데이터 등) 케이스가 테스트 목록 표에 있다. 실행 결과는 개발자가 알려 준 것만 적는다.

**G2 · 일반 · ③** 테스트는 어떤 도구로 어떻게 돌리나요? 테스트용 데이터는 어떻게 준비하나요?
충족 조건: 테스트 도구, 실행 방법을 적은 위치, 테스트용 DB·가짜 데이터 준비 방법이 있다.

**G3 · 일반 · ③** 테스트는 언제 돌리나요? 실패하면 머지를 막나요?
충족 조건: 실행 시점(PR 전, 자동 실행 등)과 실패 시 처리가 있다.

**G4 · 일반 · ④ · PM과·클라이언트와** 출시 전에 클라이언트와 함께 무엇을 확인하나요?
충족 조건: 클라이언트와 연결해 확인할 시나리오 목록, 담당, 출시를 미루는 기준이 있다.

### H 로그와 장애 대응

반영 위치 `09 로그와 장애 대응` · 문제가 생기면 로그와 재현 절차부터 확인한다

**H1 · 필수 · ③** 서버 로그에 무엇을 남기고, 무엇을 남기지 않나요? 로그는 어디서 보나요?
충족 조건: 남길 정보(요청 경로, 응답 상태, 에러 내용 등), 남기지 않을 정보(비밀번호, 토큰, 개인정보), 로그를 보는 위치가 있다.

**H2 · 필수 · ④ · 팀 전체** 버그를 발견하면 어떤 형식으로 알리나요?
충족 조건: 보고 형식(증상, 재현 절차, 기대한 결과와 실제 결과, 관련 로그 위치)과 받는 채널이 있다.

**H3 · 일반 · ④ · 팀 전체** 서비스가 멈추면 누가 어떻게 알아차리고 먼저 대응하나요?
충족 조건: 알아차리는 방법, 1차 대응 담당, 팀에 공유하는 채널이 있다.

**H4 · 일반 · ④** 장애가 났을 때 순서대로 확인할 체크리스트가 있나요?
충족 조건: 템플릿의 장애 대응 체크리스트를 우리 서비스에 맞게 고쳐 확정했다.

### I 보안 점검

반영 위치 `10 보안 점검` · 보안은 사람이 판단한다

**I1 · 필수 · ②** API 키·DB 비밀번호 같은 비밀 정보는 어디에 두고, 누가 볼 수 있나요? 실수로 노출되면 어떻게 하나요?
충족 조건: 보관 위치(서버의 환경 변수, 호스팅 서비스 설정 등), 접근할 수 있는 사람, 저장소에 올라가지 않게 하는 방법, 노출 시 새로 발급하는 절차가 있다.

**I2 · 필수 · ③** 사용자가 보낸 값은 어디서 어떻게 검사하나요?
충족 조건: 검사하는 위치, 주요 규칙(필수 값, 길이, 형식), 잘못된 값의 에러 응답(D3)이 정해져 있다.

**I3 · 일반 · ④** 출시 전 보안 점검은 누가 무엇을 확인하나요?
충족 조건: 점검 목록(템플릿 10절 보안 체크리스트를 우리 서비스에 맞게 고친 것), 최종 판단하는 사람, AI 점검 결과(예: G-stack `/cso`)는 참고 자료로 쓴다는 결정, 발견 사항 처리 방법이 있다.

**I4 · 일반 · ③** 외부 라이브러리를 추가할 때 무엇을 확인하나요?
충족 조건: 추가 전 확인할 것(필요성, 관리 상태 등)과 버전 관리 방식이 있다.

### J 성능과 비용

반영 위치 `11 성능과 비용` · 무료 또는 저렴한 인프라 한도 안에서 확인한다

**J1 · 필수 · ②** 쓰는 서비스(서버, DB, 저장소 등)의 무료 또는 요금제 한도는 무엇이고, 넘으면 어떻게 하나요?
충족 조건: 서비스별로 개발자가 사이트에서 확인한 한도와 확인한 곳, 넘을 때의 대응, 비용을 누가 내는지 팀 합의가 있다. AI는 요금을 추정하지 않는다.

**J2 · 일반 · ② · PM과** 출시 후 사용자는 어느 정도로 예상하나요?
충족 조건: 예상 범위(가설로 표시)와 그 규모에서 필요한 수준이 있다.

**J3 · 일반 · ③** 느려질 만한 곳은 어디인가요? (긴 목록, 이미지, 외부 API 호출 등)
충족 조건: 후보와 대응(페이지 나누기, 인덱스 등)이 있거나 “측정한 뒤 판단” 결정이 있다. 수치는 측정한 값만 적는다.

**J4 · 일반 · ④** 사용량과 비용은 어디서 누가 확인하나요?
충족 조건: 확인 위치, 확인 주기, 담당이 있다.

### K 출시 후 안정화

반영 위치 `12 출시 후 안정화` · 결과물: 개선 반영, 안정화

**K1 · 필수 · ⑤ · PM과** 에러와 사용자 피드백이 여러 개면 무엇부터 고치나요?
충족 조건: 우선순위 기준(예: 데이터 손실·보안 → 핵심 기능 막힘 → 불편)과 팀과 함께 정하는 방법이 있다.

**K2 · 일반 · ⑤** 에러 로그는 얼마나 자주 누가 보고 어떻게 정리하나요?
충족 조건: 확인 주기, 담당, 정리 방법이 있다. AI로 요약할 때는 개인정보와 비밀 값을 지운 뒤 넣는다.

**K3 · 일반 · ⑤ · PM과** 반영한 개선과 반영하지 않은 이유는 어디에 남기나요?
충족 조건: 기록 위치와 형식이 있다.

**K4 · 일반 · ⑤** 고친 뒤 정말 고쳐졌는지 어떻게 확인하나요?
충족 조건: 재현 절차로 다시 확인하는 방법과, 같은 문제를 막는 테스트를 추가하는 규칙이 있다.

### L 팀 AI 사용 규칙

반영 위치 `13 팀 AI 사용 규칙`

**L1 · 일반 · ① · 팀 전체** 누가 어떤 AI 도구를 어디에 쓰나요?
충족 조건: 사람별 또는 용도별 도구가 있다. 도구 비용은 참여자 부담임을 팀이 알고 있다.

**L2 · 필수 · ① · 팀 전체** 어디까지 AI에 맡기고, 어디부터 사람이 판단하나요?
충족 조건: AI에 맡길 일과 사람이 정할 일이 나뉘어 있고, “DB 설계와 보안은 사람이 판단한다”가 포함되어 있다.

**L3 · 필수 · ① · 클라이언트와** PR에 AI 사용을 어떻게 표시하나요? 리뷰할 때 무엇을 확인하나요?
충족 조건: 표시 형식, 리뷰어가 확인할 것, “설명하지 못하는 AI 코드는 머지하지 않는다” 규칙이 있다.

**L4 · 필수 · ① · 팀 전체** AI에 넣지 않을 정보는 무엇이고, 대신 무엇을 쓰나요?
충족 조건: 금지 목록(API 키, DB 비밀번호, 토큰, `.env` 내용, 실제 사용자 데이터, 개인정보)과 대안(가짜 데이터, 값을 가린 로그)이 있다. `.env`가 `.gitignore`에 들어 있다.

**L5 · 일반 · ③** AI 코딩 도구에 backend.md 요약을 어떻게 주고, 누가 갱신하나요?
충족 조건: 쓰는 도구, 넣는 방식(프로젝트 루트 규칙 파일: Claude Code는 CLAUDE.md, Codex는 AGENTS.md, Cursor는 .cursor/rules / 또는 대화 첫머리), 갱신 담당과 시점이 있다.

## 5 조건부 질문 모듈

A1·B1의 답과 서비스 종류로 적용 여부를 정한다. 모듈 안 필수 항목은 모듈을 켰을 때 완료 조건에 들어간다. 팀이 선택했을 때만 적용하는 항목은 선택하지 않았으면 이유와 함께 미적용으로 둔다.

### W 웹 클라이언트 — 웹 서비스일 때

반영 위치 `14 조건부 상세 규칙`의 W

**W1 · 일반 · ② · 클라이언트와** 서버를 부를 수 있는 웹 주소(CORS 허용 주소)는 어디인가요?
충족 조건: 개발·운영 환경별로 허용할 프론트엔드 주소가 있고, 모든 주소를 허용하지 않는다는 결정이 있다.

**W2 · 일반 · ② · 클라이언트와** 서버 주소(도메인)와 HTTPS는 어떻게 하나요?
충족 조건: 서버 주소, HTTPS 적용 방법 또는 호스팅 서비스가 제공하는지 확인한 결과가 있다.

**W3 · 일반 · ③ · 클라이언트와** 브라우저에서 로그인 상태를 어디에 어떻게 저장하나요? (쿠키 세션, 토큰 등)
충족 조건: 저장 방식과 위치, 그 방식에서 개발자가 확인한 보안 설정이 있거나 “로그인 없음”이다. E2와 맞는다.

### P 앱 클라이언트 — 앱 서비스일 때

반영 위치 `14 조건부 상세 규칙`의 P

**P1 · 일반 · ③ · 클라이언트와** 앱에서 로그인 토큰은 어떻게 저장하고 갱신하나요? 소셜 로그인을 쓰나요?
충족 조건: 토큰 종류·만료·갱신 방식, 앱 쪽 저장 위치를 앱 개발자와 합의한 기록, 소셜 로그인 사용 여부와 제공자가 있다. E2와 맞는다.

**P2 · 필수 · ③ · 클라이언트와** 사용자가 앱을 업데이트하지 않아도 예전 버전 앱이 깨지지 않게 API를 어떻게 바꾸나요?
충족 조건: API 변경 규칙(필드는 빼지 않고 추가만 등), 버전 표시 방식, 업데이트가 꼭 필요할 때 알리는 방법 또는 “지원하지 않음” 결정이 있다. D6와 맞는다.

**P3 · 일반 · ② · 클라이언트와** 이미지나 파일을 올리는 기능이 있나요? 어디에 저장하나요?
충족 조건: 업로드 방식, 저장 위치, 크기·형식 제한, 삭제 처리가 있거나 “업로드 없음” 결정이 있다.

**P4 · 일반 · ③ · PM과** 설치 수·일 평균 이용자·피드백 수 같은 운영 지표를 재려면 서버에 어떤 데이터나 이벤트 로그가 필요한가요?
충족 조건: PM이 정한 지표별로 서버가 남길 데이터 또는 이벤트, 서버가 아닌 곳(스토어 통계, 분석 도구 등)에서 보는 지표의 구분, 개인을 특정하지 않는 기록 방식이 있다.

**P5 · 일반 · ③ · 팀이 선택했을 때만** 푸시 알림을 보내나요? 서버에서 언제 무엇을 보내나요?
충족 조건: 보내는 조건과 내용, 기기 정보 저장 방식, 연동할 서비스(예: FCM/APNs)는 팀이 선택한 것만 적는다. 선택하지 않았으면 `미적용`(이유: 팀이 선택하지 않음).

**P6 · 일반 · ⑤ · 팀이 선택했을 때만** 인앱 결제나 광고 같은 수익 모델을 서버에서 처리하나요?
충족 조건: 서버가 맡을 일(결제 영수증 검증, 구매 상태 저장 등), 검증 방법은 해당 스토어 공식 문서 확인 필요로 남긴다. 선택하지 않았으면 `미적용`(이유: 팀이 선택하지 않음).

**P7 · 일반 · ④ · 팀 전체** 앱 심사 기간에도 서버를 켜 두고, 심사에 필요한 준비(테스트 계정 등)를 하나요?
충족 조건: 심사 기간 서버 유지 담당, 심사용 계정 필요 여부와 관리 방법(비밀번호는 문서에 적지 않음)이 있다.

### X 서비스 안 AI 기능 — 서비스가 외부 AI API를 부를 때

반영 위치 `14 조건부 상세 규칙`의 X · 팀이 AI 도구로 개발한다는 이유만으로 켜지 않는다

**X1 · 필수 · ③ · PM과** 어떤 기능에서 어떤 AI API를 부르고, 무엇을 보내나요?
충족 조건: 기능, 보내는 데이터(개인정보를 빼거나 최소화), 받은 결과의 처리 방식이 있다.

**X2 · 필수 · ③** AI API 키를 서버에만 두나요?
충족 조건: 키를 클라이언트에 넣지 않고 서버에서만 호출한다는 결정과 보관 위치(F2·I1)가 있다.

**X3 · 일반 · ③ · 클라이언트와** AI 호출이 실패하거나 느리거나 이상한 결과가 오면 어떻게 하나요?
충족 조건: 시간 제한, 실패 시 응답과 화면 안내, 다시 시도 여부가 있다.

**X4 · 일반 · ③** 호출 비용과 횟수는 어떻게 제한하나요?
충족 조건: 개발자가 확인한 요금 정보와 확인한 곳, 사용자별 또는 전체 호출 제한이 있다.

## 7 backend.md의 작성 구조

함께 제공된 `backend-template.md`를 복사해 `backend.md`로 쓴다. 템플릿이 없어도 같은 구조로 작성한다. 정해지지 않은 칸은 “미정”으로 남기고 ID를 연결한다.

상세 값은 한 곳에서만 관리한다. 예를 들어 테이블과 컬럼은 04절 테이블 표에서만, API의 경로와 권한은 05절 API 명세 표에서만 관리하고, 항목 결정에는 결론과 표 위치만 적는다.

1. 문서 상태, 서비스 종류(웹/앱), 단계, 인터뷰 모드, 켠 모듈
2. 자료 목록과 출처
3. A~L 영역별 결정과 표(도메인 모델, 테이블, API 명세, 에러 코드, 환경 변수 이름, 테스트 목록, 장애 대응 체크리스트)
4. 조건부 모듈 W·P·X의 결정
5. 미정·가설, 변경 이력, 다음 대화 인계 메모
6. 전체 항목 상태표
7. AI 코딩 도구에 줄 요약

**AI 코딩 도구에 줄 요약**은 확정된 결정만으로 짧게 만든다. 기술 스택, 폴더·이름 규칙, API 공통 규칙과 에러 형식, 인증·권한 원칙, 테스트 규칙, 금지 사항(비밀 값 하드코딩 금지, 로그에 개인정보 금지 등)을 담는다. 제안·미정 상태는 넣지 않는다. 확정 내용이 바뀌면 요약도 함께 고친다. 넣는 곳은 프로젝트 루트의 규칙 파일(Claude Code는 CLAUDE.md, Codex는 AGENTS.md, Cursor는 .cursor/rules)이다. 작업 순서(계획 먼저)·완료 확인·실행 전 확인받을 것·git 줄은 템플릿 문장 그대로 둔다.

## 8 피드백·변경·재개

### 8.1 버그·장애를 AI에게 물을 때의 형식

```text
증상: 무엇이 어떻게 안 되는지
재현 절차: 문제를 다시 일으키는 순서
기대 결과와 실제 결과:
관련 로그: 비밀 값·개인정보를 지운 부분만
최근 바뀐 것: 배포, 코드, 설정
요청: 원인 후보를 가능성 높은 순서로, 확인 방법과 함께
```

AI는 원인을 단정하지 않고 후보와 확인 방법을 제시한다. 같은 문제를 세 번 고쳐도 해결되지 않으면 멈추고, 지금까지 확인한 것과 남은 가설을 정리해 사람에게 넘긴다. 해결되면 K4에 따라 재현 절차로 다시 확인하고 테스트를 추가하도록 안내한다.

### 8.2 변경을 기록하는 방식

변경 요청을 받으면 먼저 기존 결정과의 차이, 영향받는 테이블·API·클라이언트, 다시 확인할 항목을 정리한다. API가 바뀌면 클라이언트 개발자에게 알릴 내용을 함께 만든다. 변경 후 본문, 표, 상태표, 변경 이력을 함께 고친다. 이전 결정은 지우지 않고 변경 이력에 남긴다.

### 8.3 다음 대화에서 이어갈 때

최신 `backend.md`가 첨부되면 서비스 종류, 현재 단계와 버전, 인터뷰 모드, 켠 모듈, 항목 상태표, 「다음 대화 인계 메모」를 먼저 읽는다. 이미 확정된 답은 다시 묻지 않고, 충돌과 이번 단계의 남은 필수 항목부터 처리한다. 대화를 마칠 때는 인계 메모를 갱신한다.

## 9 최종 점검과 출력

AI는 최종 출력 전에 아래를 점검하고 결과를 짧게 보고한다.

- 서비스 종류에 맞는 모듈(W 또는 P)과 X 모듈의 적용 여부가 정해져 있다.
- 기본 55개와 켠 모듈의 모든 ID가 상태표에 한 번씩 있고 누락·중복이 없다.
- 확정 항목은 충족 조건·근거·정한 사람(역할)이 있고, 미적용 항목은 범위 근거가 있다. 제안 상태의 DB·보안 결정을 확정으로 세지 않았다.
- 18절 상태표가 본문 항목의 상태와 같고, 기능 ID가 prd.md와 같다.
- 도메인 모델·테이블 표·API 명세 표·에러 코드 표가 서로 맞는다. (모든 엔티티에 테이블이 있고, 모든 API에 인증·권한과 에러가 있다.)
- 문서와 답변 어디에도 비밀 값, 실제 사용자 데이터, 개인정보가 없다. 환경 변수는 이름만 있다.
- 실행하지 않은 테스트·배포·점검을 했다고 쓰지 않았고, 수치와 요금은 개발자가 확인한 것만 있다.
- 남은 미정 항목의 영향과 담당자가 있다.
- AI 코딩 도구에 줄 요약이 최신 확정 내용과 같다.

개발자가 요청하면 맨 끝에 「— 문서 끝 —」 줄까지 포함한 완전한 `backend.md`를 제공하고, 요약에는 버전, 이번 단계에서 채운 항목, 남은 필수 항목, 다음 단계에서 채울 항목을 적는다. 파일 생성 기능이 없으면 Markdown 전체를 코드 블록으로 제공하고 저장할 파일명을 안내한다.

## 이 프로토콜의 적용 범위

항목 수, 필수 목록, 3단계 인터뷰 방식은 스위프 팀 프로젝트에 맞춘 운영 설계이며 외부 표준이 아니다. 질문에 나오는 도구는 예시이며 모두 쓸 필요는 없다. 도구 비용은 참여자 부담이고, 요금제와 기능은 바뀔 수 있으니 각 사이트에서 확인한다.

- [Claude](https://claude.ai/) / [ChatGPT](https://chatgpt.com/) : 대화하듯 질문하는 기본 AI. 에러 로그 해석, 설계 검토
- [Cursor](https://cursor.com/) : AI가 들어간 코드 편집기
- [Claude Code](https://www.claude.com/product/claude-code) / [Codex](https://openai.com/codex/) : 터미널에서 AI에게 코드 작업을 맡기는 도구
- [G-stack](https://github.com/garrytan/gstack) : Claude Code용 도구 모음(영어). 백엔드는 `/plan-eng-review`(서버 구조·데이터 흐름·예외 상황·테스트 계획 정리), `/investigate`(버그 원인 후보 확인), `/cso`(보안 점검), `/review`(실제 서비스에서 문제가 될 버그 찾기)를 참고한다. 결과는 참고 자료이며 판단은 사람이 한다.
