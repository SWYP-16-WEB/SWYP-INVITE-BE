# Git 컨벤션

## 작업 순서

1. 이슈를 먼저 만든다. 제목은 `<type>: <제목>`, 담당자는 본인. 이미 있으면 그 번호를 쓴다.
2. `main`에서 `<type>/<이슈번호>-<짧은-설명>` 브랜치를 만든다.
3. 작업하고 커밋한다.
4. PR을 올린다. 본문에 `close #이슈번호`를 적는다.

세부 규칙은 아래 각 절을 따른다.

## 브랜치

- `main`: 항상 배포 가능한 상태. 직접 push 금지, PR로만 병합.
- 작업 브랜치: `main`에서 분기하고 병합 후 삭제.

```
<type>/<이슈번호>-<짧은-설명>
```

예: `feat/12-invitation-create`, `fix/27-rsvp-duplicate`

## 커밋 메시지

```
<type>: <제목> (#이슈번호)

<본문 - 선택>
```

예: `feat: 초대장 생성 API 추가 (#12)`

| type | 용도 |
|---|---|
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 코드 개선 |
| `test` | 테스트 추가·수정 |
| `docs` | 문서 |
| `chore` | 빌드, 설정, 의존성 |

- 제목은 한글, 50자 이내, 마침표 없이 "~추가", "~수정"처럼 명사형으로 끝낸다.
- 커밋 하나에는 한 가지 변경만 담는다.
- 본문에는 무엇을 했는지보다 왜 했는지를 적는다.
- `Co-Authored-By` 같은 트레일러는 넣지 않는다.

## Pull Request

- 제목은 `<type>: <제목>` 형식. 이슈 번호는 넣지 않는다(병합 시 PR 번호가 자동으로 붙는다).
- 본문에 `close #이슈번호`를 적어 이슈를 자동으로 닫는다.
- 리뷰 승인은 당분간 필수로 두지 않는다. 자동 빌드가 통과하면 병합한다.
- Squash merge로 병합해 `main`에는 PR당 커밋 하나만 남긴다.
- 병합 메시지 제목은 `<type>: <제목> (#PR번호)`, 본문은 변경 요약 서너 줄로 정리한다.
- 병합 전 `./gradlew build` 통과 필수. PR을 올리거나 고치면 GitHub Actions가 같은 명령을 자동으로 돌린다(`.github/workflows/build.yml`).

## backend.md 수정

- `docs/backend.md`만 고치는 이슈·PR·커밋의 제목은 `docs: backend.md v0.NN`으로 하고, 무엇을 왜 고쳤는지는 본문에 적는다. 예: `docs: backend.md v0.22 (#27)`
- 문서 PR은 한 번에 하나만 열고, 버전은 `main`의 다음 번호를 쓴다. 버전 줄과 변경 이력의 같은 자리를 고치므로 둘이 함께 열려 있으면 충돌한다.
- 에러 코드 표와 테이블 표의 행은 코드와 같은 PR에서 고친다. 문서만 먼저 고치면 `ErrorCodeTest`와 `SchemaTest`가 실패한다.
- 그 기능 PR에서는 그 행만 고치고 버전은 올리지 않는다. 버전, 변경 이력, 그 밖의 설명은 문서 PR에서 고친다.
